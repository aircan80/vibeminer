# Item classification labels v1

Capability `item-classifications-v1` provides optional exact-build source labels through `items.classifications`. It is advertised only when a real classification service is composed. Labels never gate core Items readiness. Additive capability `item-subclass-labels-v1` is advertised only when that service supports the reviewed composite Subclass lookup and v2 request policy.

Parameters are flat `productId`, `buildIdentity`, `sourceRegion`, `researchLocale` (`enUS`), current Items `artifactId`, ordered `itemIds`, optional boolean `includeSubclass` (default false) and optional `policyRevision` (default `classification-label-index-v1`). Only `classification-label-index-v1` and `classification-label-index-v2` are accepted. Public batches contain 1–50 canonical unsigned32 decimal strings, including zero and 4294967295. Preserve order and duplicates. Reject unknown revisions, numeric JSON IDs, unknown parameters, arbitrary table/key/path/URL authority, stale features and invalid contexts before preparation. Source keys come from admitted compact Item fields.

The batch returns exact `context`, Items `artifactId`, the actual requested `policyRevision`, one source descriptor per requested kind and one outcome per input ID. Each outcome contains `itemId`, `admitted`, `class` and `subclass`; subclass is null only when not requested. Source descriptors contain kind, state, exact original TableDataSnapshot when available, index artifact identity and typed problem. A source state describes target availability/coverage, independently of whether any Item key resolves.

Absent or explicit v1 policy preserves the original behavior, including `includeSubclass:true`: admitted Items receive explicit unsupported Subclass outcomes without acquiring that prerequisite, and stale optional target authority fails the entire demand. Clients request v2 only after observing `item-subclass-labels-v1`; an older engine receives the old request shape without the new policy field. A v2 request against a classification service without Subclass support fails before work with `ITEM_SUBCLASS_UNSUPPORTED`, including class-only v2 requests. Identical v1 and v2 requests are distinct shared demands.

Values contain state, attributed numeric `sourceKeys`, optional exact `text`, optional navigable `target`, `observedCandidates` and typed `problem`. States distinguish ready, emptyText, invalidText, missingItem, fieldUnavailable, keyOutOfRange, notFound, ambiguous, incompleteTarget, unavailable, protected, unsupported and corrupt. Ready has nonempty untrimmed text; emptyText has exactly an empty string; all other states have null text. A complete unique target retains table/row/column and copy identity for ready, emptyText, invalidText and text-limit unsupported. Counts describe observed emitted candidates, including copies. Partial zero/one candidates remain incompleteTarget; observed duplicates remain ambiguous. No fallback text or absence claim is inferred.

Class lookup selects verified Item.ClassID and ItemClass.ClassID with the reviewed signed32-to-signed8 policy, and only ItemClass.ClassName_lang. Target table is `b977271e` / FDID1140189. Explicit v2 with `includeSubclass:true` also resolves `(Item.ClassID, Item.SubclassID)` against `(ItemSubClass.ClassID, ItemSubClass.SubClassID)`, both strict signed8 target fields, selecting only DisplayName_lang. Target table is `95d8638f` / FDID1261604. Source SubclassID must first be canonical unsigned8: impossible source values -1 and 256 are unavailable fields, while validated 128–255 are out of the target range; 255 never matches target -1. Neither record ID, a single SubclassID nor unrelated text substitutes for the composite key or label. Original VerboseName and DisplayFlags stay in table evidence.

Class failures preserve numeric evidence and useful Items rows. Each optional source fails independently. For explicit v2, a stale target invalidates only its own source and target-dependent values with retryable unavailable `ITEM_CLASSIFICATION_STALE`, retires that cached session and preserves the independently authorized other kind. Missing Item, unavailable source fields and out-of-range numeric keys remain truthful. Cancellation, shutdown and stale Items authority terminate the request for either policy. Class artifacts remain v1 with unchanged keys/bytes; only Subclass artifacts use the v2 file format. The batch policy describes query behavior rather than requiring matching artifact-format revisions for both kinds.

The application service has one producer, four shared demands and eight total subscriptions including stopping consumers. Host additionally holds at most **two classification publication permits**, acquired after cheap validation and before application preparation, through actual terminal stdout flush. Other requests wait cancellation-aware inside the existing 32 active-request transport bound without preparing or retaining completed batch payloads. Two matching admitted requests still share their producer and preserve independent cancellation. `request.cancel` acknowledges cancellation separately from terminal cleanup. Ordinary `EngineProgress` uses increasing request-correlated sequence, current stage, measured units and optional truthful denominators. Navigation alone does not cancel a started application-owned request. Shutdown cancels requests and awaits producer/subscription retirement and actual terminal publication before disposing the store and shared prerequisites.

The complete serialized UTF-8 success envelope **including request ID, both source proofs, both labels for every Item, JSON escaping and terminating newline** is at most 512 KiB. Host streams serialization into a fixed 512 KiB-minus-newline sink and emits the frame only after complete encoding; rejected output never builds its entire expanded JSON or publishes a partial success. Only one Host classification encoding sink exists at a time, charged through actual stdout flush, so output backpressure cannot multiply buffers. An oversized result returns `ITEM_CLASSIFICATIONS_RESULT_LIMIT`; text and outcomes are never truncated. Optional label display is limited to 4,096 UTF-16 code units and 16 KiB strict UTF-8 per label; oversized labels return unsupported with `ITEM_CLASSIFICATION_TEXT_LIMIT` and retain their exact target for full table evidence. Store-side bounded-result refusal is also typed. Failure envelopes share the same bound and oversized failures become a fixed safe typed reply. Primitive/schema limits supplement runtime exact-context, signed-width, UTF-16/UTF-8 and state/evidence checks; schema does not establish source admission.
