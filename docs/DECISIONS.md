| D065 | Refresh part superseded by D077 (an engine change wait, not only re-reads while a figure moves): Supersedes D059's Downloaded rule (a percentage only after a complete presence check, only for builds with a saved job): the engine keeps a running stored figure per admitted DL ledger and the desktop reads it through a new bounded `download.summaries` method, not `discovery.read`/`readAll` | #5. A separate method because the figure moves on its own while the discovery page and its cursor do not, and polling a page of full build projections every second would be wasteful. Stored means a verified receipt (payload, table content or metadata) for the exact EKey and length, with no known corruption of those bytes and no missing observation from a later presence check. Every write that can change that (new receipt, corruption recorded or cleared, absence found or repaired) appends the EKey to `stored_changes` in the same transaction; one `StoredCoverageWorker` applies those changes to every admitted ledger's 4096-bit pages, and counts content already on disk once when a ledger is first admitted (state `counting` until then). | D066 | 100% means every object in the build's download manifest plus the encoded object behind every ROOT-listed file the manifest does not cover, every locale and platform variant (owner decisions on #5) | Scope `downloadManifestAndRootAllVariants`, measured after Open, not inside it. Open admits the manifest as before; the background `RootScopeWorker` then reads ENCODING and ROOT one build at a time at background priority, through the shared acquisition pipeline and background CPU and staging permits, so interactive work comes first. A ROOT file is covered when any EKey of its CKey is a manifest member; an uncovered one adds the first EKey ENCODING lists for it, with its exact encoded size, so one stored object counts for that file as each manifest object counts once. The worker publishes the manifest ledger extended with those objects (one merge, no sort) and records the build's scope as measured; until then the Downloaded figure says Counting… and the scope is "measuring". At most 6,000,000 distinct ROOT CKeys. ## Working implementation defaults

Implementation clarification for D055: use empty public geometry Sources on failed preparation unless a complete pair passed the coherent final fence. Preserve truthful dependency/stage problems and current C2 metadata. Capped metadata records may use finite≤256KiB CPU serialization/comparison units with a scheduling turn afterward; effects may synchronously snapshot an immutable≤128KiB bridge binding before their first await. Neither exception permits I/O, whole-workflow CPU ownership or a claim that all parsing is cooperative. The desktop16MiB envelope counts reachable application buffers, explicit graphics reservations and active responses; driver/RSS/GC retention is measured separately and cannot be acknowledged as reclaimed by JavaScript disposal.

Schema definition data is a separate future decision; we will write the interpreter ourselves and preserve provider attribution if such data is introduced.

## Performance rationale

C# was selected by the owner after comparing Node and modern .NET. A C# engine suits binary processing, bounded parallel work, and adapting the Java implementation. Expected performance is not a measured speedup. Compare representative inventories, table decoding, database publication, and model preparation before setting budgets or making performance claims.
