What is proposed, and what can the application report today?

These designs propose keeping the user in Discover until the useful inventory/index and exact target are prepared. Required metadata admission and inventory preparation remain separate application responsibilities. Current production can enter the C overview after required metadata is admitted while inventory preparation continues; changing that entry gate requires approval and implementation.

Metadata opening already defines coarse stages, optional wire-byte totals and verified metadata requirements. Known bytes permit a download-step percentage; reaching 100% does not mean verification or inventory preparation is complete. The concrete inventory preparation backend currently supplies coarse stages without processed/total counters. The 64% mapping-index state illustrates proposed page/decoded-byte instrumentation with a known authenticated denominator; it is not an existing UI capability, a known record total, or an overall preparation percentage. SQL index size is never called downloaded data. Future final verification, ROOT/IN/DL/DS resolution, sealing and target issuance remain distinct work.

Cancellation is cooperative: show Stopping preparation until the worker retires. Verified complete shared objects and ready indexes can be reused after revalidation; unfinished staging is not a resumable percentage. Current production has one build session and retires preparation when a different build is selected; continuing a job while browsing another build is an explicit new lifecycle proposal. Browsing while preparation runs and explicit resume/retry behavior are proposals that need lifecycle and resource-budget review. They do not turn on Download all, allow a second job automatically, repair corrupt bytes silently, or imply that all payload content is retained. No fake ETA or weighted overall percentage is shown.
